## 当前状态

已按精确清单退役 58 个已跟踪前端页面、API 和共享选择器文件。执行前逐项核对 tracked 状态、工作区边界和叶文件属性，并在 `.runtime/p0-05-retirement-backup` 保存相对路径备份；逐文件 SHA256 一致后才移除源文件。`P0-05-delete-manifest.txt` 记录实际清理清单。活库菜单检查由主代理完成：现有仓储菜单 11 项不包含本清单的 10 个仓储模块；质量管理菜单 6 项也不包含批次追溯。源码 SQL 和静态路由未发现这些模块的菜单/路由项，因此当前无需新增菜单迁移 SQL。

- `productsales/line.vue` 去掉通知行选择器，产品选择统一使用现有 `ItemSelect`；销售出库行保留原有可编辑批次号字段。

- `wmstock/index.vue` 批次号改为纯文本展示，并移除 `getBatch` 点击请求。批次编码字段保留。

## 引用扫描证据

删除前扫描确认：通知选择器引用仅来自被退役的通知页面和入库/销售单表单；盘点计划选择器仅被盘点页面引用；`batchSelect` 仅被条码、退货、盘点和杂项收发页面引用；`api/mes/wm/batch.js` 仅被批次台账、QC batchtrace 和上述批次选择器调用。上述依赖已解除后，相关文件按清单退役。删除后再次扫描 `ktg-mes-ui/src`，无存活 JS/Vue 文件引用这 58 个清单文件。`api/mes/md/batchconfig.js` 属物料批次规则配置，必须保留；打印模板中的 `ITEM_BATCH` 和其它收发单的批次标签打印也保留。

清单只包含 `ktg-mes-ui` 中已跟踪的页面、组件和 API 文件，不包含批次字段、后端记账逻辑、数据库内容、物料批次配置或打印模板。批次追溯 UI 的额外影响是 QC 前向/反向追溯入口一并退役；当前前端只调用无对应后端的 batch API，现有活库质量管理菜单也没有批次追溯入口。

## 手动验收步骤

**准备数据：** 使用有仓储和物料查询权限的测试账号；准备一个可选物料、一个供应商、一张可编辑入库单及其仓库/库位信息；准备一条可查询库存记录（例如 `DEMO-BATCH-01`）。产品销售/销售退货完整页面验收前，需要先处理已有 P0-01/P0-02 路由问题并准备客户、物料和对应批次数据。禁止用访问未注册的 `productsales` 路由作为通过证据。

1. 从「仓储管理 → 物料入库」打开列表，使用查询和刷新。新建入库单时确认表头可以直接填写采购订单号、供应商选择仍存在且没有到货通知选择器；取消新建，不保存。预期网络请求只涉及仍有效的入库、物料、供应商和编码接口，不请求 arrivalnotice/arrivalnoticeline。
2. 在测试环境已存在的草稿入库单上执行编辑和查看：物料行的选择按钮打开现有物料选择器，选择后显示编码、名称、规格和单位；填写批次号，上架阶段补齐仓库、库位和库区，提交执行前应校验完整性。取消编辑后刷新列表并再次查看，确认无前端异常。本轮浏览器只读抽查没有保存/执行操作；如需验证保存，使用可丢弃的测试单据，确认成功后刷新仍可读，且网络中没有到货通知 API 请求。
3. 在「库存现有量」打开列表，筛选 `DEMO-BATCH-01` 并查询，预期返回对应一行。批次号是普通文本，点击不打开弹窗且不发 `/mes/wm/batch/{id}` 请求；刷新后继续显示批次编码。其它库存筛选、冻结操作不作为本次修复承诺。
4. 通过浏览器检查「产品销售出库」及「销售退货」前，先修复既有 P0-01/P0-02 路由注册问题。修复前本次仅做代码/构建验证：发货通知选择器及 API 引用已经移除，销售订单号 `soCode` 保留；退货行批次号为手动输入。端到端页面、保存和执行状态均未在本次验收中通过。
5. 在「供应商退货」草稿行验证批次号仍可手输；应按源单准确输入批次编码。需要保存验证时只使用可丢弃测试单据，刷新后确认字段回显，且不请求 `/mes/wm/batch`。
6. 在条码管理新建条码时，当前字典应显示物料产品条码、小包装条码、库存条码；物料产品条码类型的物料搜索可打开并列出物料。若其他部署的字典包含 `BATCH`，代码会过滤该选项，此情况未在当前活库实测。条码批量打印入口独立保留，不属于本次移除范围。
7. 确认本地菜单没有 10 个退役仓储模块和 QC 批次追溯入口。旧环境可能仍保存菜单记录；如发现旧入口，应在部署前用经审查且精确限定的菜单迁移清除，不直接操作活库。
