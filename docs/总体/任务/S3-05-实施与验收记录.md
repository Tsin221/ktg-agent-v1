# S3-05 物料入库安全执行：实施与验收记录

日期：2026-10-13。范围：已有入库单的服务端预览、原页面执行、持久化结果回读及库存维度修复。

## 做什么、预期得到什么

| 工作 | 预期结果 |
| --- | --- |
| 服务端预览已批准入库单的实际明细和版本 | 用户看到物料、正数量、单位、批次和仓库/库区/库位；表头或明细变化后旧版本执行被拒绝 |
| 执行前验证来源行、物料主数据、单位及仓储层级 | 无明细、坏引用、错误单位/位置或非正数量不触发库存写入 |
| 原 `PUT /mes/wm/itemrecpt/{id}` 继续调用统一执行服务 | 原页面和后续 Agent 路径共用幂等、锁和事务，不存在页面绕行 |
| 页面为一次确认保留操作 ID，执行后查询持久化回执 | 响应丢失时可用原 ID 核实；只在终态、流水关联和回执一致时显示成功 |
| 修复库存维度键的批次表达式 | 两行不同批次产生两条余额；同维度并发仍合并为一条余额且准确累加 |

## 实现

- `GET /mes/wm/itemrecpt/{id}/execution-preview` 返回单据号、状态、版本和逐行预计增加的库存。两次确认之间若有编辑，执行服务持有表头锁并检查版本，返回 `DOCUMENT_VERSION_CONFLICT`。
- `GET /mes/wm/itemrecpt/{id}/operations/{operationId}` 回读持久化回执，并核对单据终态、实际流水 ID 集合及操作与流水关联数。两个新读接口及旧执行接口均要求入库编辑权限。
- `POST /mes/wm/inventory-operations` 仅接受 `ITEM_RECEIPT_EXECUTE`，要求调用端提供操作 ID，并与旧入库 `PUT` 调用同一服务；领料动作不经此入口开放。
- 入库来源查询核验物料编码/单位，以及仓库→库区→库位的 ID 关系。执行服务同时校验行 ID、来源类型/单据、正数量和两位精度、批次及必需维度。
- 原页面预览后用预览版本和稳定 UUID 调旧 `PUT`；会话内保留 UUID，收到未知结果时先查原操作，避免换 ID 盲目重试。页面对预览文字进行 HTML 转义。
- S3-04 原迁移动态 SQL 中的空字符串引号少一层转义，生成的 `stock_dimension_key` 表达式将批次吞入前一个表达式，导致不同批次余额合并。原迁移已修正，新增 `20261013_s3_05_stock_dimension_repair.sql` 修复已迁移数据库，并登记于迁移脚本。

已使用旧表达式执行过入库的目标库，迁移前须按流水审计同物料、同位置的不同批次余额；修复生成列只纠正后续唯一性，不能自动拆分历史上已合并的余额。

## 验证

- Java 8 模块编译通过。`InventoryOperationServiceTest`：8 项，7 通过、1 项专用 MySQL 并发用例按条件跳过。覆盖两行预览、过期版本、第二行故障回滚、响应重放及查询。
- 专用 MySQL 库 `ktg_s304_atomicity_test` 应用修复迁移两次成功。`WmTransactionAtomicityTest`：11 项全部通过，包括真实库存服务的两行不同批次入库、同维度并发、重复执行、余额/流水/终态/回执一致及故障回滚。新增两行用例实际库存为两条余额、合计 `3.50`，两条正向流水且只执行一次。
- 前端用项目 Node 16 完成生产构建；仅有既有资源体积警告。系统 Node 22 与旧 webpack 不兼容，沙箱禁止构建线程进程，所以验证时临时关闭并行；临时配置已清理。

## 独立库验收

- 验收库为 `ktg_s208_acceptance`。执行前核查无空库存数量、无缺失的库存必需维度、无重复库存维度；仅对该库依次应用 S3-02、S3-03、S3-04、S3-05 迁移。执行前库存样本 `S3FIX-B01=10.00`、`S3FIX-B02=3.00`，没有本次新批次的余额或流水。
- `scripts/tests/s3-05-prepare-approved-receipt.ps1` 通过业务接口创建两行入库单，并经 `PREPARE → APPROVING → APPROVED` 流转。入库单 `930004` 的版本为 `4`，两行数量分别为 `2.00` 和 `1.50`，批次不同，物料、单位、仓库、库区和库位引用有效。
- `scripts/tests/s3-05-acceptance-execute.ps1` 创建临时普通用户，确认未授权的预览和旧执行接口均返回 `403`；授予入库查询/编辑权限并重新登录后，预览和旧 `PUT` 执行成功。操作 ID `f90d23a1-cadd-473a-a97a-d399cd4cbeab` 的持久化结果为 `succeeded`、单据 `FINISHED`，两条正向流水对应原两行。显式 `POST /mes/wm/inventory-operations` 用同一 ID 重放返回原成功结果；换 ID 重复执行返回 `DOCUMENT_ALREADY_EXECUTED` 及原操作 ID。临时用户、角色已软删除。
- 执行后数据库中，入库单 `930004` 为 `FINISHED`、版本 `5`；新批次余额分别为 `2.00`、`1.50`，两条流水的来源行、数量和库存 ID 分别对应，原有 `S3FIX` 两批余额未变。
- 真实页面在本地前端和独立库后端上登录后，使用 `930005`（同样经业务接口审批至 `APPROVED`、版本 `4`）点击“执行入库”。预览弹窗展示两行数量、批次和位置；确认后页面显示成功及操作 ID `9222e778-05c4-4fea-9685-defdc4000e6b`，列表中该单不再显示执行按钮。数据库中该单为 `FINISHED`、版本 `5`，新批次余额 `2.00`、`1.50`，流水 `3`、`4` 分别对应来源行 `930007`、`930008`。此页面验证使用管理员登录；普通授权用户的接口路径已单独验证。
- 对保留的已批准样本 `930003`，以错误预期版本 `999` 调显式执行接口，返回 `409 / DOCUMENT_VERSION_CONFLICT`；单据仍为 `APPROVED`、版本 `0`，没有该单流水，操作记录为 `rejected`。

并发同维度、第二行故障回滚及缺失明细的完整事务断言由上述专用 MySQL 集成测试覆盖；未在独立验收库注入人为故障。验收结论限定于本地独立库与本次代码版本，不代表生产环境已发布或 Agent 写权限已开启。
