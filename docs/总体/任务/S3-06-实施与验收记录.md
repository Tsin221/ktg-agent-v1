# S3-06 生产领料安全执行：实施与验收记录

日期：2026-10-13。范围：已有领料单的两腿库存执行、预览、原页面和持久化回执。验收环境为本机独立库 `ktg_s208_acceptance`，未发布到生产环境。

## 做什么、得到什么

| 工作 | 得到的结果 |
| --- | --- |
| 核对领料行指定的库存 ID、物料、单位、批次、仓库/库区/库位和主数据 | 不存在或维度不一致的来源库存与无效行在写入前被拒绝；不会靠物料名称猜库存 |
| 汇总同一来源库存的多行数量，逐腿执行原子扣减和线边库增加 | 库存不足明确返回 `INSUFFICIENT_STOCK`；成功时每行一出一入，供应商维度跟随来源库存 |
| 核对目标线边库层级及实际流水 | 源仓不能是线边库；提交前校验两腿类型、符号、数量、位置、来源行和 `related_transaction_id` |
| 接入预览、结果回读、原页面与显式命令入口 | 页面显示逐行来源减少和目标增加，使用版本与稳定操作 ID 执行；旧 `PUT` 与显式 `POST` 共用同一执行服务和权限规则 |
| 增加服务与 MySQL 回归用例 | 覆盖过期版本、维度不符、合计库存不足、跨批次/库位、双腿回滚和重复执行 |

## 接口和保护

- `GET /mes/wm/issueheader/{id}/execution-preview` 返回 `documentVersion` 与 `movements`，每行包括来源库存 ID、可用量、来源仓储位置、目标线边库位置及转移数量。
- `PUT /mes/wm/issueheader/{id}` 接受 `X-Operation-Id` 和 `X-Document-Version`；旧页面和直接 API 均通过 `InventoryOperationService.executeIssue`。
- `GET /mes/wm/issueheader/{id}/operations/{operationId}` 回读持久化结果，核对单据 `FINISHED`、实际流水 ID 与操作关联数。
- `POST /mes/wm/inventory-operations` 现接受 `PRODUCTION_ISSUE_EXECUTE`，并按动作分别检查领料或入库编辑权限。页面仍以查询回执确认成功，不把请求响应丢失当作执行失败。
- 预览不锁库存；执行在表头锁与事务内重新读取和校验，库存扣减 SQL 保留 S3-04 的足量谓词。源库存被别的事务先扣减时，失败返回 `INSUFFICIENT_STOCK`，整笔回滚。

## 验证

- Java 8 编译与 `InventoryOperationServiceTest`：11 项中 10 项通过、1 项专用 MySQL 并发用例按条件跳过。新增用例覆盖领料预览、过期版本、库存行不匹配和同库存多行合计不足。
- 专用真实 MySQL 库 `ktg_s304_atomicity_test` 的 `WmTransactionAtomicityTest`：12 项全通过。新增双批次、不同来源库位的领料用例：两条来源余额分别 `5→3`、`3→2`，线边库产生两条目标余额和四条关联流水。既有用例覆盖第二腿失败的整笔回滚与原子库存竞争。
- 前端在项目 Node 16 下生产构建通过；本机沙箱禁止构建线程进程，验证时临时关闭并行构建，配置已恢复。

### 独立库流程与数据库核对

1. `scripts/tests/s3-06-prepare-approved-issue.ps1` 通过业务接口建立领料头与两条来源库存行，经 `PREPARE → APPROVING → APPROVED`；来源为实体仓 `930001/930001/930001`，目标为线边库 `200/200/200`。`930003` 执行前两批来源为 `10.00/3.00`、无该单流水。普通用户无编辑权限时预览和旧执行路由均返回 403；授权后执行成功，操作 ID `7811b0ff-a1d2-40a8-a4f4-b4099c5b3f56`。四条流水 ID `14–17` 为 `-2/+2/-1/+1`，入库腿分别关联出库腿 `14/16`；来源余额为 `8.00/2.00`，线边库为 `2.00/1.00`，单据 `FINISHED`、版本 `5`，操作关联数为 `4`。同 ID 显式 `POST` 重放返回原结果，换 ID 返回 `DOCUMENT_ALREADY_EXECUTED`。临时普通用户与角色已软删除。
2. `930004` 经业务接口批准后，第一批请求 `9.00` 而可用 `8.00`；预览和执行均返回 `INSUFFICIENT_STOCK`，单据仍 `APPROVED`、版本 `4`，没有该单流水。错误预期版本 `999` 返回 `DOCUMENT_VERSION_CONFLICT`。随后 `930005` 请求剩余的 `8.00/2.00`，恰好足量成功；四条流水 `18–21`，两批来源余额归零，线边库累计为 `10.00/3.00`。
3. 为故障和并发样本，先经业务入库流程建立 `930014`，生成实体仓两批 `930023/930024`，余额 `2.00/1.50`。领料单 `930006` 也经业务状态流转并预览。临时 MySQL 触发器仅让此单的 `ITEM_ISSUE_IN` 写入失败，得到 `EXECUTION_FAILED / failed`；来源仍为 `2.00/1.50`，单据仍 `APPROVED`、版本 `4`，该单流水和执行占有记录均为 `0`。触发器已移除，数据库中同名触发器数为 `0`。随后对 `930006` 两个不同操作 ID 同时执行：一条成功，一条 `DOCUMENT_ALREADY_EXECUTED`；仅四条流水 `25–28` 落库，来源变为 `1.00/0.50`，线边库两批各增加 `1.00`，成功、拒绝和先前失败回执各一条。
4. 原网页登录独立库后，`930007` 的预览弹窗展示两批各自的来源减少 `1.00/0.50` 和线边库目标增加 `1.00/0.50`；点击“确认领料”后页面显示操作 ID `381e0fd1-8f34-4812-88cd-898c9101b66d`。数据库核对：单据 `FINISHED`、版本 `5`，来源余额均为 `0`，四条流水 `29–32` 按行和 `related_transaction_id` 配对，回执为 `succeeded`。页面验证使用管理员，普通授权用户的接口路径另行验证。

这些数据只属于独立验收库。悬浮 Agent 的库存写工具和生产发布仍按 S3-08/S3-09 处理，当前未开放。
