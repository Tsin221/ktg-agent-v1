## 交付

- `20261013_s3_02_inventory_operation.sql` 新建回执、已执行单据键和回执流水关联三张 InnoDB 表。`operation_id` 为回执主键；`(action_type, document_type, document_id)` 为已执行单据主键。流水关联表对 `transaction_id` 唯一且有外键，不在 `wm_transaction.source_doc_id` 上设唯一键，允许领料一单多条流水。
- 两个旧执行路由接受可选 `X-Operation-Id`（UUID）。缺省时服务端生成并返回 ID。登录用户 ID、用户名由服务端会话取得。请求摘要由动作、服务端确定的单据类型、单据 ID 和规范化预期状态计算；同 ID 异请求返回 `OPERATION_ID_CONFLICT`。
- 统一服务先提交 `executing` 预留回执，再在一个数据库事务中认领单据唯一键、锁定单据、写库存和流水、关联流水、置单据 `FINISHED` 并提交 `succeeded` 回执。任何一步失败时该事务回滚，预留回执在独立事务中记为 `failed` 或 `rejected`。响应丢失后，同 ID 重放读取已提交回执。执行进程在预留后崩溃可能留下 `executing`，须由 S3-07 的恢复查询处理，不能将其当作成功或换新 ID 重试。
- 现有 `PUT /mes/wm/itemrecpt/{recptId}`、`PUT /mes/wm/issueheader/{issueId}` 已进入该统一服务。两者保留现有 `edit` 权限。旧页面不传 ID 时仍由单据唯一键防重复。

## 迁移前检查

对**目标数据库**先执行以下只读查询并保存结果。若有异常，不应静默删除历史业务行；先按单据号、流水 ID、库存余额和业务审计记录核实，再制定人工修复或保留为历史例外的决定。代码对已有流水的单据拒绝再次执行。

```sql
-- 同一来源行、同一流水动作的历史重复；领料两腿动作不同，不会误报。
SELECT source_doc_type, source_doc_id, source_doc_line_id, transaction_type,
       COUNT(*) AS n, GROUP_CONCAT(transaction_id ORDER BY transaction_id) AS transaction_ids
FROM wm_transaction
WHERE source_doc_type IN ('IR', 'ISSUE')
  AND source_doc_id IS NOT NULL AND source_doc_line_id IS NOT NULL
GROUP BY source_doc_type, source_doc_id, source_doc_line_id, transaction_type
HAVING COUNT(*) > 1;

-- 已有流水但单据仍非完成状态，或单据已完成但没有流水。
SELECT 'IR' AS document_type, h.recpt_id AS document_id, h.recpt_code AS document_code,
       h.status, COUNT(t.transaction_id) AS ledger_count
FROM wm_item_recpt h LEFT JOIN wm_transaction t
  ON t.source_doc_type = 'IR' AND t.source_doc_id = h.recpt_id
GROUP BY h.recpt_id, h.recpt_code, h.status
HAVING (ledger_count > 0 AND h.status <> 'FINISHED')
    OR (ledger_count = 0 AND h.status = 'FINISHED');

SELECT 'ISSUE' AS document_type, h.issue_id AS document_id, h.issue_code AS document_code,
       h.status, COUNT(t.transaction_id) AS ledger_count
FROM wm_issue_header h LEFT JOIN wm_transaction t
  ON t.source_doc_type = 'ISSUE' AND t.source_doc_id = h.issue_id
GROUP BY h.issue_id, h.issue_code, h.status
HAVING (ledger_count > 0 AND h.status <> 'FINISHED')
    OR (ledger_count = 0 AND h.status = 'FINISHED');
```

迁移本身可重复执行，不修改历史单据或库存。首次上线需在代码切换前应用迁移；`scripts/apply-db-migrations.ps1` 已登记该文件。已有流水但没有新回执的历史执行不能伪造一个成功回执，统一服务拒绝再执行并交由人工核对。
2026-10-13 对现有独立验收库 `ktg_s208_acceptance` 只读检查：`wm_transaction` 为 `0` 行，上述来源键重复数为 `0`；本任务未对该库应用迁移或执行库存动作。

## 保留、清理和回滚

成功回执、单据、流水与关联行组成同一审计链，不随 Agent 会话过期清理；当前没有自动 TTL。失败与拒绝回执同样保留，具体法定保留期须依部署方的审计政策确定。在保留期内不得单独删除已执行单据、流水、回执或关联行。独立验收环境结束后，应先归档完整数据库及快照，再整体废弃专用验收库；不能只删除样本单据。

回滚应用代码后，新表应保留以维护已产生的审计证据。仅当三张新表均为空、且已确认没有依赖它们的新执行结果时，才可以按 `wm_inventory_operation_transaction`、`wm_inventory_executed_document`、`wm_inventory_operation` 的顺序删表。若已有成功回执，回滚方案应是恢复兼容代码或整体恢复经核验的数据库快照，不能删除回执让旧路由重新记账。

## 验证证据

在三个专用库 `ktg_s302_idempotency_test`、`ktg_s302_concurrent_test`、`ktg_s302_java_test` 运行；原 `ktg_s208_acceptance` 未执行库存写入。使用 `scripts/tests/s3-02-mysql-fixture.sql` 和同目录并发/回滚 SQL，迁移连续运行两次均成功。
`SHOW INDEX` 实测确认操作回执 `operation_id` 主键、已执行单据三列复合主键、操作与流水关联唯一键均存在。
复现 Java/MySQL 测试时，先新建**空的** `ktg_s302_java_test`，按顺序导入 `scripts/tests/s3-02-mysql-fixture.sql` 与 `20261013_s3_02_inventory_operation.sql`；在本机加载 `use-java8.ps1`、`use-local-secrets.ps1`，设置 `KTG_S302_MYSQL_DB=ktg_s302_java_test`，先单独运行 `InventoryOperationServiceTest`，再在第二次 Maven 进程中单独运行 `InventoryOperationRestartReplayTest`。后者依赖前者留下的成功回执，不应与全套测试同一次进程混跑。并发 SQL 的 A/B 脚本分别送入两个 MySQL 客户端，先启动 A，在它持有未提交键时启动 B。

| --- | --- |
