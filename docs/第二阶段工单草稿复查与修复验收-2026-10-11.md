## 真实链路记录（2026-10-11）

环境为独立数据库 ktg_s208_acceptance、Java 18080、Agent 18001、Vue 18081；使用当前登录的 admin 和真实 DeepSeek 模型。测试前库内只有基线工单 WO-DEMO-A01-001；测试物料、产品 BOM 和工单均使用 S2R 前缀。

1. Agent 预览 S2R-AGENT-20261011-01，产品 S2R-PROD-01、数量 7、需求日期 2026-10-25。确认前数据库该编号计数为 0。确认后为 PREPARE、版本 0、两条 BOM 14 和 3.5；Agent 返回成功且 bom_verified=true。
2. Agent 预览改量 9、名称、备注和日期；确认前数据库仍是数量 7、版本 0。确认后版本 1，BOM 18 和 4.5；再次确认返回同一结果，无重复写入。浏览器刷新列表和详情，字段及 BOM 与数据库一致。
3. 网页悬浮助手再把数量改为 10，备注改为“S2R 网页助手回读”；结果卡显示修改成功、PREPARE、版本 2、BOM 已核验（2 行）；数据库数量 10，BOM 20 和 5。
4. 原有工单页面创建 S2R-WEB-20261011-01，再按真实键盘交互编辑为数量 6；数据库版本 1、BOM 12 和 3，刷新后仍可见。自动化脚本最初只向数字控件写入文本而未触发 Vue 的变更事件，第一次保存了控件默认值 0.01；改用键盘输入并失焦后回读正确。这是自动化输入方式造成的偏差，不计为产品缺陷。
5. 不存在的近似编码、同名产品及数量 0 均未生成草稿；重复工单编号的确认返回 KTG_CONFLICT，库中无重复编号。
6. 空批次号实测起初失败，是旧的可执行 jar 仍内嵌旧 Mapper。增量 package 虽显示成功，未更新 ktg-admin.jar 内的 ktg-mes 依赖。停止服务并执行 clean package、检查内嵌 Mapper 后重启，重新提交空批次，数据库 batch_code 长度为 0、版本递增。项目启动脚本本身已使用 clean package。

## 普通账号与权限复验（2026-10-12）

在同一独立验收库通过管理员用户接口创建临时账号 s2r_operator_20261012，登录成功，用户 ID 3，非管理员。最初分配系统现有 common 角色，产品列表、产品 BOM 列表、工单 BOM 列表、工单列表四个接口均返回业务码 403“没有权限，请联系管理员授权”。这证实了默认 common 角色不能完成工单草稿流程；拒绝发生在写入前。

随后为该账号配置临时专用角色 s2r_draft_operator_20261012，仅授予页面路径及工单草稿所需权限：产品列表/详情查询、产品 BOM 列表、工单列表/详情/新增/编辑、工单 BOM 列表。重新登录后上述四个查询接口均返回业务码 200。未授予工单删除或物料/BOM 写入权限。

恢复 S2R-PROD-01 与两行产品 BOM 测试数据后，使用此非管理员身份调用真实模型和 Agent：预览编号 S2R-OP-20261012-01、数量 4、需求日期 2026-10-28 时工单计数仍为 0；确认创建成功，ID 2、PREPARE、版本 0、BOM 已核验 2 行。该账号回读工单数量 4、工单 BOM 数量 8 和 2。随后预览改量 5 时原单仍是数量 4、版本 0；确认编辑成功，版本 1、BOM 已核验 2 行。该账号回读数量 5、BOM 10 和 2.5。独立 MySQL 查表确认两行 BOM、数量、版本，create_by 与 update_by 均为该普通账号。

验收后通过业务接口删除该测试工单、用户和角色，并清理测试产品与 BOM。用户和角色采用系统软删除：del_flag=2，角色关联 0，已无可登录的活动测试账号；S2R 工单和物料均为 0，原基线工单仍为 1。临时密码文件已删除，审计日志保留。本轮先验证接口及模型链路；后续普通账号网页补验和故障清单见下节。
