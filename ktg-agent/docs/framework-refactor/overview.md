# KTG Agent 框架化重构总体说明书

版本：V1.2（总体设计说明）  
日期：2026-11-25  
状态：总体重构方向及功能取舍已确认，尚未进入详细设计和实施。  
审查基准：`ktg_agent_v1` 的 `main` 分支，提交 `26e93f5`。

> 本说明书描述重构的目标、功能边界、技术方向和需要达到的效果。它不是详细设计、实施任务书或接口契约，不规定具体代码结构、类和函数、数据库表、API 字段、事件格式、配置值、依赖版本、实施顺序，也不表示任何重构已经完成。下一阶段应根据实际验证另行确定实现方案。

## 一、项目定位与重构目标

KTG Agent 是面向 MES 生产主管场景的面试展示 Demo，不是生产级制造系统或自研通用 Agent 平台。项目重点是展示对工单、库存、备料、质量、生产追溯等制造业务的理解，以 Agent 自主组合业务工具、结合真实 MES 数据分析问题，并在用户确认后进行受控操作。

当前 Python Agent 自行实现了 HTTP 服务、模型适配、执行循环、消息与上下文、工具发现、任务预算、事件流、会话持久化等大量通用基础设施。审查基准下共 48 个 Python 源文件、12,682 物理行（含空行和注释，不含测试）；这不意味着所有代码均应删除，但足以说明框架化简化的价值。

本次重构的目标是：

- 以成熟框架接管通用 Agent 能力，减少重复建设和长期维护负担。
- 保持已有 MES 业务能力及正常演示体验，不因框架替换削弱 Agent 自主分析、规划及工具组合能力。
- 将自研工作的核心回归 MES 业务理解、工具设计、业务权限与确定性执行。
- 降低架构理解成本，便于后续独立开发、维护及面试讲解。代码量减少是结果之一，不是唯一评价标准。

## 二、重构边界

本次重构对象仅为自研 Python `ktg-agent` 服务。允许为已经确认的能力取舍做必要的前端兼容调整，但不重新设计 MES 前端或改变其主要演示交互。

以下内容必须保留：

- 现有八项业务工具：产品统计、分仓现存量、工单概览、工单备料与剩余用料、工单质量、双向生产追溯、业务编码识别及受控工单操作方案。原有业务含义、授权和结果真实性要求不变。
- 真实 MES 用户身份、当前权限、对象范围和业务合法性校验。
- 业务操作方案、用户确认、实际执行、回执核实与防重复执行。未经确认的 MES 写入不得由模型直接执行。
- 多轮会话、实时回复、结构化业务结果、自主规划与工具组合、工具执行进度、任务清单、运行中调整方向、追加任务、停止运行、断线重连和用户主动继续任务等主要使用体验。
- MES 页面感知能力，帮助 Agent 理解用户当前查看的业务对象和查询范围。

明确不重构第三方 Java MES，不修改现有 MES 数据模型、业务规则、接口语义或演示业务数据；不恢复已退役的历史业务工具，也不借本次重构扩展新业务范围。具体业务边界以 [Agent 建设工程](README.md)、[MES 业务使用手册](../ktg完善文档/MES业务使用手册.md) 及 [受控业务操作](06-受控业务操作.md) 为依据。

## 三、总体技术方向

框架选型：**Pydantic AI 为 Agent 核心的第一选择**。以其原生模型接入、工具调用、执行循环、消息与上下文、流式事件等通用能力为基础，先验证现有 DeepSeek 和关键交互，再正式迁移。不同时引入多个 Agent 框架，也不为框架另建不必要的通用系统。

| 层级 | 推荐选型 | 承担的职责 |
| --- | --- | --- |
| Web 服务 | FastAPI、Uvicorn | HTTP 服务、路由、请求与响应、SSE 传输 |
| 数据校验 | Pydantic | 通用数据结构与输入校验 |
| Agent 核心 | Pydantic AI | 模型调用、Agent 循环、工具管理、消息、事件、运行限制及上下文管理 |
| 任务规划 | 优先评估 Pydantic AI 的原生 Planning 能力 | 自主计划、步骤状态及进度展示 |
| 模型 | 继续使用 DeepSeek（当前 `deepseek-flash`） | 推理、自然语言理解、自主选择工具；保留其他模型接入能力 |
| 持久化 | SQLite | 会话、任务、工具执行状态及业务操作的必要记录 |
| MES 业务层 | 现有 KTG 工具与受控执行能力 | 业务事实查询、权限、操作确认、执行及回执 |

Pydantic AI 具体能力、版本和配套依赖须验证后确定。若原生能力不满足已确认的体验或业务约束，进行必要的轻量业务适配，不因此重新开发一个通用框架。它也不替代 MES 权限、业务校验、操作确认或回执。

下面是概念上的职责分工，不是代码模块或部署拓扑：

```text
现有 MES 前端
          │
Web 接口与实时事件适配（FastAPI / Pydantic）
          │
Agent 通用运行能力（Pydantic AI）── DeepSeek 等模型
          │
KTG 业务工具与受控执行层
          │
现有 Java MES

SQLite 支撑必要的会话、任务、运行状态和业务操作记录。
```

## 四、确认的重构决策

以下 D-01 至 D-14 是本轮讨论达成的方向性决策，编号用于后续讨论和设计引用，不代表任务书编号或实际代码实现。

| 编号 | 决策 | 必须保留或达到的效果 |
| --- | --- | --- |
| D-01 | 删除独立摘要 Run | 保留自动摘要，将其视为正常上下文处理的一部分，不再维护摘要专属生命周期。 |
| D-02 | 删除手动上下文压缩 | 由系统自动决定压缩时机，不要求用户手动触发。 |
| D-03 | 删除精细 Token 结算 | 保留基础用量统计、模型及工具调用次数、时间、单次输出等运行限制，必要时配置简单总用量限制。 |
| D-04 | 删除工具结果落盘与二次提取 | 通过合理分页、结构化输出和必要摘要控制结果规模，不新增读回落盘文件的机制。 |
| D-05 | 进程重启不自动续跑 | 保留任务、工具执行状态及结果，用户主动继续；业务结果未知时核实原回执，保证幂等。 |
| D-06 | 取消自研工具搜索与加载 | 根据当前用户权限直接提供可用业务工具，模型仍自主选择、组合和调用，实际执行继续校验权限。 |
| D-07 | SSE 实时流与持久状态分离 | 实时文字增量临时缓存，完整消息及关键执行状态持久化；保留断线重连。 |
| D-08 | 简化任务清单 | 保留自主规划、最新步骤状态、进度展示和主动续办；删除任务专属的四项复杂机制。 |
| D-09 | 旧 Agent 历史不迁移 | 新架构从全新会话数据开始，不维护旧表结构或历史版本兼容层；MES 业务数据及必要业务回执不受影响。 |
| D-10 | 继续使用 SQLite | 框架管理通用消息与历史，应用保存必要状态；不引入 ORM、额外 Agent 数据库或分布式存储。 |
| D-11 | Pydantic AI 作为核心框架第一选择 | 优先由一个成熟 Agent 框架接管通用运行能力，通过关键能力验证后正式采用。 |
| D-12 | 运行中交互遵循框架原生语义 | 保留 Steer、Follow-up 和停止运行，取消为复刻原有行为而建设的自研消息调度及复杂运行阶段控制；不恢复跨进程待处理指令。 |
| D-13 | 删除自研专项重规划机制 | 保留模型自主调整计划及更新任务清单的能力，取消专门的重规划触发、提示注入及检查点记录；保留正常错误反馈、必要运行限制和业务结果核实。 |
| D-14 | 保留 MES 页面感知 | 利用当前页面、筛选范围及已选业务对象等信息理解用户意图，保留现有集成体验；页面信息不能替代真实业务查询及权限校验。 |

选择这些方向有实际项目依据：本地正式演示数据库的只读聚合显示，57 次已完成用户 Run 对应 214 次模型请求，没有发生独立摘要、启用总 Token 停止阈值或工具结果落盘。173 次工具调用中有 78 次属于搜索、加载（约 45%，不等同于额外模型请求数）；17,811 条文字增量约占全部事件的 87%。这些是审查时本地演示的数据，不代表云端、未来负载或所有使用场景，也不是直接删除业务状态的理由。

## 五、重构后的能力说明

### 5.1 Agent 运行与工具管理

用户发起任务后，Agent 根据上下文、用户目标及当前授权自主选择可用工具，进行必要的多轮模型推理和工具调用，组织真实业务结果并回答用户。当前工具规模无需独立搜索、加载步骤，未来工具规模明显扩大时再考虑使用成熟框架的按需发现能力。

工具是否对模型可见与是否准许实际执行是两个不同的判断。即使模型尝试调用一个不可用工具，也必须由服务端依据已确认的业务范围和当前权限拒绝；不能把工具隐藏当作权限控制。继续保留必要的调用限制、超时、输入校验和错误反馈，不为具体用户问法硬编码流程。

保留现有 MES 页面感知能力。用户在工单、物料等业务页面发起对话时，Agent 可以结合当前页面及相关对象信息理解“这张工单”“当前物料”等指代，减少重复输入并体现与 MES 的集成价值。页面信息仅作为辅助上下文，不是实时业务事实、权限或写入授权的依据；仍须通过授权工具查询与核实，用户明确要求的对象优先于页面默认对象，无法确定时请求澄清。不引入专门的页面感知框架，也不扩大现有页面信息采集范围。

### 5.2 会话、上下文与运行限制

完整原始会话历史与模型实际看到的上下文分开。短对话直接使用所需历史，长对话自动压缩旧消息并保留必要摘要及近期完整对话。摘要应保留任务目标、关键业务对象和未完成事项；工具调用与结果保持完整对应。

摘要是派生上下文，不是 MES 实时事实、权限或操作回执的权威来源。必要时重新查询业务数据；摘要失败时可在模型窗口允许的范围内回退到近期完整历史，明确上下文不足，不以编造事实掩盖历史缺失。

保留基础 Token 使用量和必要的 Run 级运行上限。未收到真实模型用量时如实表示未知，不能当作零；达到限制后停止启动超出允许范围的工作，保留真实状态。删除逐模型调用独立落盘、精细结算与重启恢复账本，不删除正常运行控制。

### 5.3 任务清单

任务清单是 Agent 的规划与进度工具，不是另一套工作流调度器。复杂任务可以由模型自主拆解，持续更新最新步骤状态，根据用户新要求调整计划，并在必要时从已有状态主动继续任务。简单请求无需强制创建清单。

本轮明确取消四项专属机制：完整任务版本历史、每步骤独立工具调用配额、任务保存次数限制、专用收尾模型调用及预算。统一使用 Run 级运行限制。保留稳定任务及步骤标识、最新状态、必要证据及结果引用，允许必要的轻量并发一致性判断；未完成、未核实的步骤不得为了展示而标记成功。

重规划属于正常 Agent 执行能力，不另设重规划流程。模型依据最新用户要求、工具结果和任务进度自主修正方案，必要时更新任务清单；无法继续时说明阻塞、保留未完成状态，必要时请求用户补充信息。取消现有专门的重规划原因检测、额外重规划提示注入及检查点记录。普通工具失败依赖真实错误反馈、合理重试与运行上限处理；涉及 MES 写入结果未知时，仍必须核实实际状态，不得盲目重复执行。业务安全约束不依赖模型是否进行了重规划。

### 5.4 流式输出及中断恢复

用户可以看到实时文字、工具调用过程、任务进度及最终业务结果。文字增量用于实时展示，不逐个持久化；完整消息、必要工具记录、任务进度和终态等关键状态持久化。

不同中断场景分别处理：

| 场景 | 预期行为 |
| --- | --- |
| 网页刷新或网络断开 | 服务仍在运行时重新连接原任务，恢复可展示进度和结果，不重发请求。 |
| 服务进程重启 | 原活动任务进入中断终态，释放新任务的运行资格；不自动续跑。已有关键状态仍应可查询。 |
| 用户主动继续未完成任务 | 基于原任务、已完成工具及结果开展后续工作；过期或未核实的只读事实可以重新查询。 |
| 已确认的 MES 操作结果未知 | 保留原操作标识，核实实际回执，不盲目重复执行；未发送的步骤不能被视为已执行。 |

不引入进程级持久工作流引擎，不要求恢复文字生成到一半的位置或精确回放每个历史增量。

保留运行中调整方向（Steer）、追加任务（Follow-up）和停止执行，交互及生效语义优先遵循 Pydantic AI 的原生能力，不要求完全复刻原有时序。调整方向在框架下一次模型决策机会生效，追加任务在当前工作即将完成时处理；停止后不继续启动新工作，已执行的业务操作不因调整方向或停止而撤销。取消自研复杂输入调度、运行阶段控制及跨进程待处理指令自动恢复机制；具体停止边界与前端呈现由后续验证及详细设计确定。

### 5.5 MES 业务确认与幂等

业务写入和普通 Agent 推理必须保持明确边界。Agent 负责理解用户目标、查询业务事实和准备方案；授权用户确认后，由业务执行机制校验当前条件、执行并核实真实 MES 结果。

保留已确认业务操作的稳定标识、执行状态及回执。操作请求已提交但响应丢失时，结果属于未知，需要按原标识核实，而不是重新执行。不得因重新连接、请求重试、流程中断或任务续办产生重复业务写入；未正常完成的方案准备任务也不得被伪装成可确认状态。现有权限、版本、回执及业务规则均不得削弱。

### 5.6 数据持久化与旧数据

新架构仅须保存必要的逻辑信息：会话归属、完整消息与工具结果、运行状态与基础统计、任务最新状态、业务操作确认与回执。这些是信息职责，并非指定的数据库表结构。

继续 SQLite，由最终框架负责通用消息管理和序列化，应用保存最少必要状态，不采用双重对话历史。旧 Agent 聊天、运行、事件、摘要、任务版本及 Token 明细全部不要求迁移。切换前仍需处理或保留未结算的已确认业务操作及必要的幂等记录，可保留旧库作为回退备份；不得清空 MES 本体数据或把业务操作结果随会话重置丢弃。

## 六、成功标准（总体效果）

重构成功意味着可以用更简单的架构完成原有核心演示，而非仅通过已有内部实现测试或达到某个预设代码行数。后续设计和实施应围绕以下效果验证：

- DeepSeek 能够正常完成多轮对话、跨工具 MES 查询、实体编码识别、数据分析及结构化结果展示。
- Agent 可以结合当前 MES 页面信息理解用户指代，同时不绕过真实业务查询、权限校验及操作确认。
- Agent 框架承担通用执行，已确认退役的机制不再作为新运行的独立基础设施存在。
- 任务清单可体现真实进度，用户主动续办有效；运行限制和中断不会造成虚假成功。
- Agent 能在正常执行循环中依据工具反馈自主调整计划，并支持运行中调整方向、追加任务和停止；无需独立重规划机制。
- SSE 实时输出正常，刷新、断线及服务重启分别符合第五章定义的行为。
- 用户权限、操作确认、执行结果及防重复写入不受框架迁移影响，响应丢失仍可核实原回执。
- 从空的新 Agent 持久化结构启动可用，不依赖旧会话数据；Java MES 及现有业务规则不变。
- Demo 依赖、部署和维护复杂度合理，新的业务工具可以在清晰边界内开发，不再扩展自研通用 Agent 框架。

上述是总体方案的目标和验证原则，不是具体测试用例、数据迁移脚本或实施排期。
